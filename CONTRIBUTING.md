## How to Contribute

There are many ways to contribute to Clean Labels:

### 1. **Use It and Share Feedback**
   - Adopt Clean Labels in your projects
   - Share what works and what doesn't
   - Report real-world edge cases we haven't covered

### 2. **Improve Documentation**
   - Fix typos or unclear explanations
   - Add more examples or use cases
   - Improve the specification clarity

### 3. **Propose Enhancements**
   - Suggest changes to the label set
   - Propose improvements to the convention format
   - Share edge cases and how you handled them

### 4. **Participate in Discussions**
   - Help answer questions from other users
   - Engage in specification discussions
   - Share your adoption experience

## Proposing Changes to the Convention

The Clean Labels convention is intentionally minimal and stable. Changes to the core label set require careful consideration.

### Before Proposing a Change

Ask yourself:
- Does this change make the convention simpler or more complex?
- Is this solving a real problem that many teams face?
- Can existing labels handle this use case?
- Does this maintain the "Clean Repos deserve Clean Labels" philosophy?
- Does the proposed label follow the `[Category] Description [scope]` format?

### How to Propose a Change

1. **Open an Issue**
   - Clearly describe the problem you're trying to solve
   - Explain why existing labels don't cover the use case
   - Provide real-world examples where you've encountered this gap

2. **Include These Details**
   - **Problem:** What workflow gap are you addressing?
   - **Current Behavior:** How does Clean Labels handle this today?
   - **Proposed Solution:** The new or modified label definition
   - **Examples:** Show real issues/PRs that would use this label
   - **Impact:** How does this affect existing adopters?

3. **Be Open to Discussion**
   - The community will review your proposal
   - Be prepared to iterate
   - Accept that not all proposals will be accepted

### Types of Changes

**Minor Changes** (easier to accept):
- Clarifications to label descriptions
- Improved documentation and examples
- Edge case guidance
- Specification clarifications

**Major Changes** (require strong justification):
- Adding new labels to the core set
- Changing label names or colors
- Modifying the description format
- Removing existing labels

## Improving Documentation

Documentation improvements are always welcome!

### What to Improve

- **Clarity:** Make the specification easier to understand
- **Examples:** Add more real-world label usage examples
- **Organization:** Improve structure and navigation
- **Completeness:** Fill gaps in edge case coverage
- **Accuracy:** Fix errors or outdated information

### How to Contribute Documentation

1. **Fork the Repository**
   ```bash
   git clone https://github.com/YOUR-USERNAME/clean-labels.git
   cd clean-labels
   ```

2. **Create a Branch**
   ```bash
   git checkout -b docs/improve-specification
   ```

3. **Make Your Changes**
   - Edit the relevant markdown files
   - Follow existing formatting conventions
   - Keep language simple and direct

4. **Use Clean Commit Workflow**
   ```bash
   📖 docs: clarify scope field in specification
   📖 docs (readme): add missing combination examples
   📖 docs: fix typo in quick reference
   ```

5. **Submit a Pull Request**
   - Describe what you changed and why
   - Link to any related issues

## Discussion Guidelines

### Do:
- ✅ Be respectful and constructive
- ✅ Focus on ideas, not people
- ✅ Provide concrete real-world examples
- ✅ Listen to different perspectives
- ✅ Assume good intentions

### Don't:
- ❌ Be dismissive or condescending
- ❌ Make personal attacks
- ❌ Propose changes without real-world justification
- ❌ Argue in bad faith

## Code of Conduct

We are committed to providing a welcoming environment for everyone. Expected behavior includes:

- Using welcoming and inclusive language
- Respecting differing viewpoints
- Accepting constructive criticism gracefully
- Showing empathy toward other community members

Violations may result in warnings or removal from project spaces. Report violations to the project maintainers.

---

## Review Process

### For Documentation Changes
1. Submit pull request
2. Maintainers review within 7 days
3. Address requested changes
4. Merge once approved

### For Convention Changes
1. Open issue for community discussion
2. Allow minimum 2 weeks for input
3. Maintainers evaluate based on feedback and real-world impact
4. If approved, update specification and all docs
